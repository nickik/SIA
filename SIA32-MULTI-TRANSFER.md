# SIA32-I Multi-Register Transfer Semantics

## Status

- Applies to: `LDP`, `STP`, `LD4`, `ST4`
- Target: `SIA32-I`
- Status: **normative completion rule for v1**

This document freezes the precise exception and restart semantics of SIA pair and four-register transfers.

The architectural rule is simple:

> **Multi-register transfers are all-or-nothing with respect to recoverable architectural faults and interrupts.**

A failed instruction produces no partial architectural register update, no partial architectural memory update, and no base-register writeback.

This rule exists so operating systems can restart a faulting instruction without reconstructing partial progress.

---

# 1. Covered instructions

The rule applies to all baseline forms of:

```text
LDP
STP
LD4
ST4
```

including:

```text
plain addressing
post-increment addressing
pre-decrement addressing
```

Pair transfers cover exactly 8 bytes.

Four-register transfers cover exactly 16 bytes.

---

# 2. Complete-transfer validation

Before the instruction may architecturally complete, the processor must validate the complete transfer.

Validation includes every constituent word access and therefore includes, where applicable:

- effective-address arithmetic;
- required alignment;
- every page translation touched by the transfer;
- every relevant page permission;
- User/Supervisor access permission;
- the complete physical-address range;
- whether the target is normal memory rather than prohibited device/MMIO memory;
- other recoverable architectural access checks.

If any constituent word would fault, the entire instruction faults.

---

# 3. Load completion

For `LDP` and `LD4`, the implementation must conceptually gather all source words before changing architectural destination registers.

If any constituent load faults:

```text
all destination registers remain unchanged
base register remains unchanged
memory remains unchanged
EPC identifies the multi-register instruction
BADADDR identifies the failing constituent address
```

On success, all destination registers become architecturally updated as one instruction completion.

The implementation may internally perform the memory reads serially or in parallel.

Internal partial progress is not architectural state.

---

# 4. Store completion

For `STP` and `ST4`, no recoverable architectural fault may result in a partially completed store sequence.

If validation of any constituent store fails:

```text
no constituent store becomes architecturally visible
base register remains unchanged
EPC identifies the multi-register instruction
BADADDR identifies the failing constituent address
```

The implementation must therefore validate the complete transfer before committing the store group.

A simple implementation may:

1. calculate every address;
2. perform every translation/protection check;
3. verify that the complete range targets ordinary writable memory;
4. only then issue the stores.

---

# 5. Page-boundary crossing

A pair or four-register transfer may cross a page boundary.

Cross-page execution is legal when every touched page satisfies the instruction's requirements.

Example:

```text
ST4 begins at the last 8 bytes of page A
    word 0 -> page A
    word 1 -> page A
    word 2 -> page B
    word 3 -> page B
```

The implementation must validate both page A and page B before architectural completion.

If page B is absent or not writable, **none** of the stores to page A or B occurs architecturally.

Likewise, a cross-page `LD4` that faults on page B modifies none of its destination registers.

---

# 6. Base-register writeback

For post-increment and pre-decrement forms, base-register writeback is part of the same architectural instruction completion.

Therefore:

```text
instruction succeeds -> base writeback occurs
instruction faults   -> base register is unchanged
```

For a pre-decrement store, the decremented effective address may be used internally while validating the transfer, but the architectural base register is not updated until the complete instruction succeeds.

---

# 7. Exception PC

Any synchronous exception generated by a multi-register transfer records:

```text
EPC = address of the LDP/STP/LD4/ST4 instruction
```

Restarting at `EPC` retries the complete instruction.

Software never needs to know how many internal constituent accesses had been attempted before the fault was detected.

---

# 8. `BADADDR`

When one constituent word is responsible for the fault:

```text
BADADDR = virtual address of the first constituent access, in architectural memory order, that fails validation
```

Architectural memory order is increasing register number to increasing address.

This gives deterministic fault reporting even if a particular implementation validates constituent accesses in parallel.

---

# 9. Interrupts

An asynchronous interrupt is never architecturally taken in the middle of a multi-register instruction.

The CPU either:

```text
completes the entire multi-register instruction
then takes the interrupt
```

or:

```text
takes the interrupt before beginning architectural execution of the instruction
```

No partial register or memory state is exposed to an interrupt handler.

---

# 10. MMIO remains prohibited

Multi-register operations remain prohibited for device/MMIO mappings.

This is essential because device accesses may have irreversible side effects and therefore cannot in general participate in the all-or-nothing prevalidation/commit model.

If any constituent physical address resolves to device/MMIO memory, the complete instruction faults before any device access occurs.

Device memory uses scalar load/store instructions only.

---

# 11. All-or-nothing does not mean SMP atomic

The all-or-nothing rule concerns **faults, traps, interrupts, restart, and architectural instruction completion**.

It does **not** make `STP` or `ST4` an atomic shared-memory transaction with respect to another CPU.

For a successful `ST4`, another coherent CPU may observe the individual word stores according to the SIA memory-ordering rules.

If software needs an indivisible interprocessor operation, it must use `SIA32-A` atomic instructions.

Likewise, `LDP` and `LD4` do not guarantee an atomic snapshot of multiple words while another CPU modifies those words concurrently.

---

# 12. Memory order of a successful transfer

For a successful transfer, constituent memory operations have the defined logical order:

```text
lowest register number / lowest address first
then increasing register number / increasing address
```

Example:

```asm
ST4 r4:r7, [r8]
```

has logical component order:

```text
[r8 +  0] <- r4
[r8 +  4] <- r5
[r8 +  8] <- r6
[r8 + 12] <- r7
```

This ordering interacts with the strong normal-memory model in [`SIA32-MEM.md`](SIA32-MEM.md).

The implementation may use wider internal memory paths as long as observable behavior is equivalent.

---

# 13. Physical hardware failure

The all-or-nothing rule applies to **recoverable architectural exceptions** such as:

- page faults;
- permission faults;
- alignment faults;
- invalid physical mappings discovered during validation.

An unrecoverable physical failure that occurs after commit has begun — for example an uncorrectable memory-system or machine-check failure — may be treated as a fatal machine error rather than a restartable instruction exception.

This distinction prevents ordinary page-fault behavior from becoming dependent on impossible rollback of physically failed memory hardware.

The platform should arrange ordinary RAM so a successfully prevalidated store does not generate a normal recoverable per-word access fault during commit.

---

# 14. Implementation strategies

The architecture does not require a particular implementation.

Possible designs include:

## Small serialized CPU

```text
calculate all addresses
walk/check all translations
buffer translated addresses
perform reads/stores
commit registers/writeback
```

## CPU with TLB

```text
translate/check complete 8/16-byte range
ensure all pages and permissions valid
perform memory operation
commit architectural state
```

## Wide memory implementation

A machine may perform pair or quad transfers with a wider internal memory operation when alignment and memory-system structure permit it.

The architectural result is unchanged.

---

# 15. Rust VM requirements

The SIA Rust full-system VM should make this behavior explicit rather than accidentally obtaining it from host operations.

Recommended execution sequence:

```text
1. decode instruction
2. derive every constituent virtual address
3. translate and validate every address
4. reject MMIO
5. for load: read all values into temporaries
6. for store: validate complete store set before mutation
7. commit register or memory results
8. commit base-register writeback
9. retire instruction
```

This becomes the differential reference for later FPGA RTL.

---

# 16. Required conformance tests

At minimum test:

- pair load entirely within one page;
- pair store entirely within one page;
- quad load entirely within one page;
- quad store entirely within one page;
- every post-increment form;
- every pre-decrement form;
- transfer ending exactly at a page boundary;
- transfer crossing into a valid second page;
- transfer crossing into an unmapped page;
- transfer crossing into a read-only page during store;
- User transfer crossing into a supervisor-only page;
- transfer whose first word is valid and later word faults;
- transfer whose final word faults;
- load fault leaves every destination register unchanged;
- store fault leaves all memory unchanged;
- fault leaves base register unchanged;
- fault reports instruction `EPC`;
- fault reports deterministic first failing `BADADDR`;
- interrupt cannot expose partial completion;
- MMIO target is rejected before any side effect.

---

# 17. Summary

The v1 rule is:

```text
LDP/STP/LD4/ST4

recoverable success:
    complete whole instruction

recoverable fault:
    no destination update
    no memory update
    no base writeback
    EPC = instruction
    BADADDR = first failing constituent address

interrupt:
    before or after instruction, never during

MMIO:
    prohibited

SMP atomicity:
    not provided
```

This gives SIA the restart behavior needed by a small protected kernel without introducing hidden partial-transfer state.
